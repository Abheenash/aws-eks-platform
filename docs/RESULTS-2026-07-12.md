# Live run results — 2026-07-12

Real evidence from an end-to-end `terraform apply → deploy → drills → destroy`
burst. All numbers below were measured, not estimated. Cluster: `eks-platform`
(EKS v1.31, 2× t3.small), us-east-1. Destroyed after capture.

## Provisioning

- `terraform apply` — **66 resources added, 0 errors**.
- 2 nodes `Ready` (~110s after node group create), AWS Load Balancer Controller
  `2/2`, Metrics Server `1/1`.
- App deployed: 2 pods spread across both nodes; ALB provisioned and `active`
  with **both targets healthy**.
- Load-balancing baseline (20 requests): an even **10 / 10** split across the two
  pods — the Service is distributing traffic.

> Gotcha worth keeping: the box's local resolver returned a bad `100.x`
> (CGNAT/Tailscale) address for the ALB first, so a plain `curl` got `000`. The
> ALB was healthy the whole time — pinning `curl --resolve` to the real public IP
> confirmed `200`. (Same "trust the target-group health, not the local DNS"
> lesson as before.)

## Drill 1 — pod failure & self-healing

Deleted one of two pods while hammering the ALB (400 requests).

| Metric | Value |
|---|---|
| Time to a new pod `Ready` (back to 2/2) | **7 s** |
| Requests during recovery | 400 |
| Failed | **3** — 2×`502`, 1×`000` (≈ 0.75%) |
| All other requests | `200` |

**Honest finding:** this is **not** truly zero-downtime. The 502s happened in the
short window where the ALB was still routing to the terminating pod before it
finished deregistering from the target group. The surviving pod absorbed the rest.
**Corrective action:** add a container `preStop` sleep and/or raise the target-group
`deregistration_delay` so the ALB drains the pod *before* it dies — closes the gap.

## Drill 2 — Horizontal Pod Autoscaler under load

Drove CPU with 14 parallel clients hitting `/burn`.

| Metric | Value |
|---|---|
| CPU utilization (idle → loaded) | 5% → **~300%** of request (hit the 300m limit) |
| Replicas: min → peak | **2 → 6** (the `maxReplicas` cap) |
| Time to first scale-out (2 → 4) | **~45 s** |
| Time to reach max (→ 6) | **~60 s** |
| Behavior under sustained load | held steady at 6 |

**Honest finding:** one pod restarted once during peak load — its **liveness probe
tripped** because the CPU busy-loop starved the `/health` handler. Real lesson:
CPU-bound work shouldn't share the request path with the liveness endpoint;
tune the probe (or isolate the work) so saturation doesn't cause restarts.
Scale-**down** is governed by the default 5-minute stabilization window (not waited
out here, to keep the cluster's billed time short).

## Teardown

`terraform destroy` run immediately after; verified 0 EKS clusters, 0 ALBs, and
0 NAT gateways remain (commands in [`cost.md`](cost.md)). Total billed time for
the run: well under an hour → ~$0.30–0.50.
